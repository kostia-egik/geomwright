# Straight bevel gear module (`gear_bevel`)

Status: experimental, implemented create-only slice for straight bevel gears
with the ГОСТ 19624-74 macro geometry and the classic Tredgold virtual-gear
projection (G5 first stage of
[gear-transmission-concept.md](gear-transmission-concept.md)); exposed as three
MCP tools. Recorded live acceptance cases are described below; this documentation
audit has not rerun them. Circular (spiral) teeth are reserved and are not built yet.

Concise guides: [English](en/gear-bevel.md) / [Русский](ru/gear-bevel.md).
This page owns the detailed geometry, CAD plan and recorded evidence.

This module builds one straight bevel wheel from an explicit pitch cone angle.
The functional body is a dish: a flat base plate that rises through two rim
cone faces normal to the tooth (back and front) into the face cone; the tooth
ends are formed by those same cone surfaces. It is not a gear pair, not a
housing or hub, and not a strength calculation.
The architectural boundaries are in [ARCHITECTURE.md](../ARCHITECTURE.md); this
page is the user-facing contract.

## Inputs

| Field | Meaning | Notes |
| --- | --- | --- |
| Tooth type | Straight or circular | `straight` is implemented; `circular` is reserved for the next stage and is rejected |
| Standard | Basic-rack system | ГОСТ 13754-68 (default), ГОСТ 13755-2015, ГОСТ 9587-81, ГОСТ Р 50531-93, or ISO 53:1998; use `list_gear_standards` for identifiers and variants |
| Contour modification | Named variant of the standard | ГОСТ 13754-68 has one standard contour; `custom` exposes the coefficients |
| `module_mm` | Outer circumferential module `m_e` | ГОСТ 9563-60 rows |
| `tooth_count` | Number of teeth `z` | 6–400 |
| `pitch_cone_angle_deg` | Pitch cone half-angle `δ` | 5–85°; 45° is a 1:1 orthogonal pair |
| `profile_shift` | Rack shift `x` of the virtual gear | Default 0 |
| `face_width_mm` | Face width `b` along the pitch cone | Empty selects the ГОСТ 19624-74 recommendation `b = 0.285 R_e`; the report records the source |
| `rim_back_extension_mm` | Back cone face extension | Axial length of the back conical rim face behind the outer tip plane; empty selects `1.2 b sin δ` (at least 2 mm) |
| `rim_front_extension_mm` | Front cone face extension | Axial length of the front conical rim face behind the inner tip plane; empty selects `0.3 b sin δ` (at least 1.5 mm) |
| Derived coefficients | `α`, `h_a*`, `c*`, `ρ_f*` | Editable only for the user-defined modification |

The face width is checked against `K_be = b / R_e <= 0.3`; a value at or above
the outer cone distance and a dish blank without positive axial width are
rejected before any CAD work. The virtual tip thickness and the virtual
undercut are reported, not silently corrected.

Rim extensions are dish-blank heuristics, not normative rack dimensions. Schema,
calculation and Studio hints use the same defaults.

## Geometry

The macro geometry follows ГОСТ 19624-74, table 2:

- outer pitch diameter `d_e = m_e z`, outer cone distance `R_e = d_e / (2 sin δ)`;
- outer addendum `h_ae = (h_a* + x) m_e`, outer dedendum `h_fe = (h_a* + c* - x) m_e`;
- addendum/dedendum angles `tan θ_a = h_ae / R_e`, `tan θ_f = h_fe / R_e`,
  face cone `δ_a = δ + θ_a`, root cone `δ_f = δ - θ_f`;
- outer tip diameter `d_ae = d_e + 2 h_ae cos δ`, outer root diameter
  `d_fe = d_e - 2 h_fe cos δ`.

The blank is a dish, not a cone frustum. Its flat back face is offset behind
the outer tip plane by `rim_back_extension_mm` (`1.2 b sin δ` by default), its
flat front face sits behind the inner tip plane by `rim_front_extension_mm`
(`0.3 b sin δ` by default), and the rim between them is bounded by two cone
surfaces **normal to the tooth**: the back cone through the outer pitch point
and the front cone through the inner pitch point, both with axis-section slope
`cot δ`. The face cone (tip cone) closes the rim between the two tooth corners.
No tooth end is cut by an axial plane, so the ends stay square instead of
tapering to a point; the flat base plate keeps a reference diameter of
`2 r_back` where the back cone meets the back face.

The tooth profile is the classic Tredgold construction: the tooth space of the
equivalent (virtual) spur gear on the back cone is projected to the gear apex.
The virtual gear has the continuous tooth count `z_v = z / cos δ`, pitch radius
`R_v = R_e tan δ`, and the same module, pressure angle, and profile shift. Its
flank is generated by the same sharp-rack involute/trochoid core as the
cylindrical module (`build_tooth_space_flank`), so the root transition and the
tip sharpness follow the selected basic rack.

Without virtual-gear undercut, the root transition joins the involute
at its analytical contact station, with bounded local sampling. The rack's
tabulated tip radius defines a normal-offset roulette envelope, keeping the
root depth and straight flank unchanged. A missing radius retains a sharp rack.
Searching for
polyline intersections is insufficient for this tangential junction, especially
at large pitch cone angles.
Undercut profiles retain the sharp-rack baseline. This remains a nominal
Tredgold projection, not an octoid generated by a real bevel cutter.

Representation mode is `nominal`: the flanks are the Tredgold projection of the
virtual involute, not an exact spherical involute and not an octoid cut by a
real bevel cutter. The module reports
`warning.gear_bevel_nominal_projection` and makes no standard-conformity claim.

## Measurements

The report carries the outer-end controls that ГОСТ 19624-74 table 3 defines
in the back-cone development:

- outer circumferential tooth thickness `s_e = (π/2 + 2 x tan α) m_e`;
- outer chordal tooth thickness and its height on the virtual pitch circle;
- constant chord `s̄ = (π/2 cos²α + x sin 2α) m_e` and the height to it;
- virtual tip-circle tooth thickness against the 0.25 m / 0.30 m limits;
- base pitch and both chordal heights for the preview.

Over-pin and span measurements are not part of the bevel standard and are not
produced. A gear pair (`Σ`, mate tooth count, backlash, contact pattern) is a
separate assembly-level module.

## CAD plan

`build_bevel_gear_plan` produces a create-only numeric plan:

1. a dish blank: one `revolved_profile_blank` sketch with the closed `(x, r)`
   profile — flat back face, back cone, tip cone, front cone, flat front face —
   revolved 360° around the global X axis;
2. two `section_profile_sketch` cone-normal sections: the virtual tooth-space
   contour scaled about the gear apex onto the planes just outside the blank's
   back and front cones (`R_e + margin` and `R_i - margin`). The bridge creates
   the plane perpendicular to the pitch cone generatrix and measures the actual
   sketch frame from probe points before writing the contour;
3. one `loft_cut` between the two closed sections. The sections are true
   homothetic copies, so the loft side surfaces follow the projection rays of
    the Tredgold cone. The planar cut sections extend beyond the material;
    the blank's conical rim faces, not those planes, trim the tooth ends;
4. a circular pattern of the tooth-space cut, `z` instances over 360°.

The expected volume is the exact revolution volume of the dish profile minus
`z` tooth spaces. Each tooth space uses a sampled virtual contour clipped by
both end cones, both flat faces, the face cone and the actual loft section
margins. Scale integration along apex rays is analytical; planar integration
is numerical. This is not an exact spline/BREP volume. The estimate is compared
with the native single-cut removal and with the final body to within 1.5 %.

The bridge verifies one positive-volume solid, the axial extents and the radial
envelope, the physical tooth count, and the relative volume error against the
plan before the part variables and the checksummed recipe are written. The
block owns `GW_GEAR_VERSION=3`, `GW_FAMILY_CODE=10`, the full `GEAR_*` readback
fingerprint (including `GEAR_DELTA_DEG`, `GEAR_ZA`, `GEAR_ZF`), and a recipe
that restores the Studio form for a new build.

The bridge primitives that support this plan stay family-neutral:

- `conical_blank` / `revolved_profile_blank` — a closed `(x, r)` profile
  revolved around the global X axis;
- `section_profile_sketch` — a closed profile on a plane parallel to a default
  plane or perpendicular to an explicit 3D axis line; the host supplies 3D
  points and the bridge measures the actual sketch frame first;
- `loft_cut` — `ILoft` cut (`o3d_cutLoft`) between two or more closed sketches.

## Verification

The live acceptance cases are stored under `experiments/spikes/` (local,
ignored):

- straight bevel gear `m_e = 3`, `z = 20`, `δ = 45°`, default dish parameters:
  one solid, volume within 0.06 % of the dish-minus-spaces value, the expected
  axial span `[-38.139, -19.933]`, `20` pattern instances, and a verified
  recreatable block after save/reopen; the KOMPAS 3D view shows the dish plate
  with teeth ending squarely on the conical rim faces;
- `m_e = 4`, `z = 16`, `δ = 26.565°`, `x = 0.2`: one solid, 0.04 % volume
  error, `16` pattern instances, save/reopen verified.

These checks cover the solid, its bounds, the physical tooth count, and the
managed-block recipe. They do not certify the exact spherical involute, an
octoid generated by a real bevel cutter, tooth contact, or strength.

The default `m3 z20 delta45` case was rerun through the shared MCP contract on
2026-10-09: creation, native order-4 spline knots/weights, single-solid bounds,
20 teeth, and save/reopen recipe parity passed. The final plan uses C2 cubic
B-splines with simple interior knots instead of a multi-span Bezier chain:
face count dropped from 743 to 183 and creation from 91.58 to 30.03 seconds
locally. The observed volume error was 0.0121%, within the unchanged tolerance.
Section-frame conversion preserves mathematical degree versus native order
(`CURVE-001`); spline representation follows `CURVE-002`. These checks do not
certify all input combinations.

## Studio and MCP

Studio exposes the module under **Механические передачи → Зубчатые передачи**.
Studio displays three coordinated views:

- Left: an axial projection of the rim sector and its solid foundation. Teeth
  remain visible through the small end; the wavy bottom break passes through
  foundation material below the inner tooth contour. Side breaks keep their
  wavy style. Three tooth-tip surfaces show the straight longitudinal edges;
  the central tooth is marked D without color highlighting.
  Diameters `d_e`, `d_fₑ`, `d_ae` belong to the large end.
  Thin gray longitudinal lines mark the root-transition boundaries in each gap.
- Upper right: the hatched radial half of the axial section, including cone
  apex O, `B`, `b`, `R_e`, cone angles and viewing arrow D.
- Lower right: the enlarged orthographic view of the actual back-cone tooth-end
  contour, looking along the central pitch generator. It is not a section and
  is not the virtual gear profile. `s_e,proj` measures the projected pitch chord;
  rack-derived head/root heights are dimensioned on the central reference
  generator, not presented as chordal inspection heights.
  The lower and side boundaries are thin wavy drawing breaks, not part edges.

Drawing crops trim fills and longitudinal/reference lines without modifying
the calculated tooth contours or CAD geometry. The axial section is not cropped.

The two right views collapse together and stack below the sector on smaller
screens. Projection construction is owned by `studio/bevel_preview.py`, with
right-view drawing in `static/bevel-views.js`. A circular-tooth family will need
its own calculated longitudinal curves; this preview does not synthesize them.
The persisted block is read-only and recreatable from its recipe.

MCP tools:

- `preview_bevel_gear` — Layer 2 analysis, no COM;
- `create_bevel_gear` — plan with `execute=false`, write only with
  `confirm_write=true`;
- `inspect_bevel_gear` — read the managed block and its recipe.

The shared MCP/CLI contract exposes this family as `module_id="gear_bevel"`;
see [the request format](../README.md#cad-module-pilot-mcp-and-cli).
It uses the same nominal Tredgold generator and limits. Its `frame` distinguishes
width along the pitch cone from actual axial extents. `create` requires
`confirm_write=true`; `inspect` recognizes the recipe, not fresh geometry, and
returns recoverable parameters only when `data.recreatable=true`.

## Out of scope

Circular/spiral teeth (the selector reserves the value but rejects it), gear
pairs and mesh synthesis, hubs, bores, keyways, tip chamfers, cutters and
generated-exact flank surfaces, contact-pattern and strength calculations are
separate modules. Applying the teeth to an arbitrary pre-existing body is also
outside this slice: the module creates its own conical blank.
