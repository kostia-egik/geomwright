# Sketch Authoring Protocol v0

Status: design draft. It is retained for human geometry planning and must not be
treated as a public MCP schema.

Черновик для обсуждения. Это не агентский чеклист и не окончательный стандарт.
Документ описывает человеческий порядок проектирования сложных KOMPAS-эскизов в
`kompas-mcp`: как сначала понять инженерный смысл эскиза, потом описать его
топологию, и только после этого превращать в генератор.

Машинная форма этого же процесса находится в
[`sketch-authoring-agent-protocol.md`](sketch-authoring-agent-protocol.md).

## Зачем нужен этот документ

Сложный эскиз в KOMPAS почти никогда не ломается по одной причине. Обычно
смешиваются сразу несколько слоёв: смысл детали, выбор базовых точек,
топология контура, helper-геометрия, ограничения, размеры, таблица переменных,
особенности COM API и поведение 3D-операции. Если начинать с кода, эти слои
начинают исправляться одновременно, и работа превращается в длинное расследование.

Цель этого протокола — не заменить CAD-диагностику, а уменьшить количество
случаев, когда она вообще нужна. Диагностика отвечает на вопрос “что сломалось”.
Этот документ должен заставлять нас раньше ответить на вопрос “что именно мы
строим”.

Протокол нужен не для каждого прямоугольника или окружности. Он включается,
когда эскиз имеет несколько смысловых зон, дуги, сопряжения, helper-геометрию,
несколько параметров, нестандартную базу координат, или когда его будет
потреблять чувствительная операция: вращение, выдавливание, вырез, sweep,
evolution, pattern или составная операция.

## Главный принцип

Сложный эскиз сначала проектируется как инженерная схема, а не как набор
объектов API.

До написания генератора должны быть понятны четыре вещи:

1. какой контур является рабочим и каким стилем линий он реализован;
2. какие элементы являются вспомогательными и каким стилем они отделены от
   рабочего профиля или траектории;
3. какие размеры действительно управляют геометрией;
4. какая операция будет потреблять эскиз и что для неё считается корректным
   входом.

Если эти четыре вещи нельзя объяснить словами, код писать рано. Можно делать
маленький probe, можно читать документацию, можно рисовать схему, но нельзя
сразу строить полноценный параметрический генератор.

## Базовые термины

Этот документ использует несколько терминов, которые должны иметь физическое
отражение в KOMPAS-эскизе, а не только существовать в описании.

Для автоматизированного рисования в рамках этого протокола значимыми считаются
три категории стилей: основной, осевой и вспомогательный/тонкий. Остальные
визуальные различия могут быть полезны человеку, но не должны вводить новую
операционную семантику без отдельного решения.

Рабочая геометрия — геометрия, которую должна использовать операция. Для
автоматизированного построения она должна быть выполнена основным стилем линии.
Для замкнутых эскизов основной стиль задаёт рабочий профиль. Для незамкнутых
эскизов основной стиль задаёт рабочую траекторию или другой открытый контур,
если именно его должна потреблять операция.

Осевая геометрия — геометрия, выполненная осевым стилем. В операции вращения она
используется как ось вращения. В остальных случаях осевой стиль допустим как
графическое отображение оси или как будущая база для симметрии, но не как
обычная helper-линия.

Вспомогательная геометрия — геометрия для построений внутри эскиза: центры,
радиусы, контрольные высоты, измерительные базы, линии привязки. Она должна быть
выполнена вспомогательным или тонким стилем и не должна использоваться вовне как
источник профиля, траектории или оси операции.

Контур — связанная последовательность элементов эскиза. Контур может быть
замкнутым или незамкнутым. Это различие обязательно надо указывать до кода.

Замкнутый профиль — замкнутый контур основного стиля, который задаёт область для
операции: вращения, выдавливания, выреза или профиля sweep. Базовое правило для
наших генераторов: один operation sketch должен иметь один рабочий замкнутый
профиль. Несколько профилей возможны теоретически, но пока считаются исключением
и требуют отдельного решения, чтобы не заставлять automation угадывать регион.

Незамкнутый контур — открытая цепочка элементов. Он используется для траекторий,
дополнительных построений, направляющих, путей sweep/evolution и похожих задач.
У незамкнутого контура всегда должны быть явно определены начало, конец и
направление обхода. Его нельзя описывать как профиль, если он не задаёт область.

Переменная — именованный параметр KOMPAS/генератора, который используется в
размерах, формулах или интерфейсе сценария. В этом документе переменные делятся
на ведущие и производные. Ведущая переменная управляется пользователем или
внешним сценарием. Производная переменная вычисляется из других параметров и
попадает в таблицу только если действительно помогает управлять, читать или
проверять модель.

Проекционная связь — связь, при которой элемент текущего эскиза базируется на
спроецированном внешнем объекте: ребре, точке, вершине, объекте другого эскиза
или 3D-геометрии. В таком эскизе источником истины является не локальное начало
координат, а projected object и constraints, которые привязывают рабочую или
вспомогательную геометрию к этой проекции.

Полная определённость эскиза — состояние, при котором KOMPAS считает геометрию
достаточно связанной ограничениями и размерами. Это важный критерий законченности
параметрического эскиза, но не единственный источник истины: в сложных эскизах
`ConstraintsState` может давать осечки или меняться после reopen/update. Поэтому
полная определённость должна проверяться вместе с preflight, operation success и
readback.

## Паспорт эскиза перед кодом

Для сложного эскиза перед реализацией нужен короткий “паспорт”. Это не должен
быть большой документ. Обычно достаточно 20-40 строк, но эти строки должны
снять самые опасные неопределённости.

Паспорт отвечает на вопросы ниже.

Какая операция будет использовать эскиз? Например: вращение, выдавливание,
вырез, профиль sweep, путь sweep, auxiliary/reference sketch.

Что является главным рабочим контуром? Надо указать его тип: замкнутый профиль
или незамкнутая траектория. Замкнутый профиль описывается в порядке обхода:
`A -> B -> arc C -> D -> ... -> A`. Незамкнутый контур описывается как
`start -> ... -> end`, с явным началом, концом и направлением. Если порядок
обхода не известен, значит контур ещё не спроектирован.

Какие точки имеют инженерный смысл? Не “точка 3” и не “правый конец дуги”, а
`outer_base`, `body_inner`, `bend_center`, `wire_profile_center`,
`path_finish_end`, `full_height_gauge_point`. Для каждой такой точки желательно
понимать, почему она существует.

Какой тип базирования используется? Надо выбрать элемент, от которого ведётся
отсчёт, и явно указать его роль. В обычном автономном эскизе этот элемент по
возможности привязывается к началу координат, координатной оси или базовой
плоскости локальной СК. Если эскиз основан на окружности или наборе элементов по
окружности, центр координат обычно должен находиться в центре этой окружности.
Если эскиз должен зависеть от существующей 3D/2D-геометрии, базой может быть
проекция внешнего объекта. Тогда надо указать projected source, projected result
и constraints, которыми рабочая или вспомогательная геометрия привязана к этой
проекции. Если геометрический ноль не совпадает с измеряемой точкой, это надо
указать явно.

Какие стили линий используются? Надо явно разделить элементы основного, осевого
и вспомогательного стиля. Основной стиль — источник рабочего профиля или
траектории. Осевой стиль — ось вращения или ось/симметрия. Вспомогательный/тонкий
стиль — только внутренние построения, которые не используются вовне.

Какие параметры являются ведущими? Ведущая переменная — это то, чем должен
управлять пользователь или внешний сценарий. Если переменная появилась только
потому, что её удобно было посчитать внутри генератора, она не обязана попадать
в таблицу переменных.

Какие параметры производные? Производные переменные допустимы, но только если
они имеют понятный смысл, полезны для формул или диагностики, и не создают
ложного ощущения управляемости. Информационная переменная “для красоты” опасна,
если её формула хрупкая или зависит от скрытых геометрических допущений.

Какие инварианты должны быть верны после построения? Например: для замкнутого
профиля — один closed contour, одна компонента, нет branch nodes и
self-intersections; для незамкнутой траектории — одно начало, один конец,
правильное направление и нет лишних ответвлений; для вращения — ровно одна
axis-line; для sweep — профиль расположен на правильном конце пути. Для
параметрических эскизов отдельным инвариантом обычно является полная
определённость или осознанно зафиксированное исключение, почему она недостижима
или ненадёжна для данного случая.

## Базирование эскиза

Базирование отвечает на вопрос: от чего эскиз отсчитывает свою геометрию и какие
свободы убраны в самом начале.

Обычный автономный эскиз должен по возможности иметь базовый элемент, связанный с
началом координат, координатной осью или базовой плоскостью локальной СК. Это
уменьшает число свобод, убирает лишнее смещение и делает модель читаемой. От
такой базы удобно ставить размеры к остальным элементам.

Для круговой геометрии нормальная база обычно находится в центре окружности или
центре раскладки элементов по окружности. Это касается окружностей, тел
вращения, радиальных массивов, пружинных сечений и других случаев, где смысл
детали задаётся радиусом или центром.

Проекционное базирование используется, когда эскиз должен быть привязан не к
своей локальной СК, а к уже существующей геометрии модели. В этом случае
спроецированный объект становится базовым anchor. Рабочая или вспомогательная
геометрия должна быть связана с ним явными constraints: например,
`merge_points`, `point_on_curve`, vertical/horizontal от projected point или
projected edge.

Проекционное базирование нельзя заменять ручным копированием координат, если
нужна связь с исходной геометрией. Координаты могут помочь для первичного
построения или диагностики, но source-of-truth — projection link. Также не надо
дублировать размеры на projected geometry только для имитации исходника: если
проекция корректна, она уже несёт связь с внешним объектом.

Если inspection не может определить источник projection constraint, нельзя
угадывать его по близкой геометрии. Источник надо подтвердить через UI,
readback, координаты или отдельный probe. Это уже зафиксировано в
`CAD_PATTERNS.md` как правило для projection references.

Пример из проекта: в bent coil эскиз на angled plane оказался ненадёжным при
базировании от локального origin. Более устойчивым контрактом стало спроецировать
3D-точку начала тела в целевой sketch и привязать center axis к projected point.
Такой эскиз базируется от проекционной связи, а не от собственной системы
координат.

## Общий порядок работы

Сложный эскиз должен расти слоями. Нельзя одновременно менять топологию,
ограничения, размеры и таблицу переменных. Это главный источник долгих
расследований.

Сначала проектируется смысловая схема. На этом этапе мы ещё не думаем о COM API.
Нужно понять, что означает каждая зона детали, где находятся базовые точки, что
является внутренней/наружной стороной, где начало и конец, какие размеры должны
остаться устойчивыми при изменении параметров.

Потом фиксируется топология. Здесь определяется порядок точек и сегментов, какие
элементы выполняются основным стилем, какие осевым, какие вспомогательным или
тонким, какие дуги идут по часовой стрелке или против, где находится ось, где
путь, где замкнутый профиль. Топология должна быть понятной без размеров.

Потом строится geometry-only версия. Это минимальная геометрия без попытки
сделать её красиво параметрической. На этом этапе надо доказать, что операция
вообще может съесть эскиз данного класса: вращение видит замкнутый профиль и
ось, выдавливание видит область, sweep видит замкнутый профиль и незамкнутый
путь. Если geometry-only не работает, поверх неё нельзя наращивать constraints.

Потом добавляются ограничения. Ограничения должны стабилизировать уже понятную
геометрию, а не пытаться исправить плохо спроектированную топологию. Если
constraints меняют смысл контура, это сигнал, что схема была недостаточно
описана.

Потом добавляются размеры. Размер должен цепляться к named target, а не к
случайному индексу линии. Хороший target имеет имя, которое говорит, какой
физический смысл он измеряет: `outer_normal_face`, `bend_inner_radius_line`,
`wire_profile_diameter`, `full_height_gauge_offset`.

Потом добавляется таблица переменных. На этом этапе важно не раздувать её.
Переменная должна либо управлять деталью, либо поддерживать устойчивую формулу,
либо быть действительно полезной для чтения модели. Всё остальное лучше оставить
внутренним расчётом генератора.

Потом выполняется live verification и readback. Успешное создание размера или
успешный `Update()` не доказывают, что эскиз корректен. Для операционного
эскиза нужно проверить контур, 3D-операцию и сохранённую/переоткрытую модель.

## Один сложный эскиз или несколько простых

Перед тем как усложнять sketch, надо отдельно спросить: действительно ли эта
геометрия должна жить в одном эскизе?

Один сложный sketch удобен, когда у детали есть один естественный операционный
контур и все helper-элементы обслуживают именно его. Но если sketch начинает
содержать несколько независимых смысловых областей, несколько будущих операций,
несколько альтернативных регионов или смесь замкнутого профиля и открытой
траектории, он часто становится хрупким не из-за KOMPAS, а из-за неверной
декомпозиции.

Иногда правильное решение — не “лучше зафиксировать constraints”, а разделить
модель на несколько sketches и операций. Это особенно важно для automation:
человек в UI может выбрать нужный регион, а генератору лучше давать меньше
поводов выбирать.

Разделение на несколько sketches не является поражением. Это способ сохранить
понятный контракт каждого эскиза: один sketch отвечает за один потребитель и
одну инженерную мысль.

## Вариативность по типу потребителя

Различия надо описывать не по примитивам геометрии, а по тому, кто потребляет
эскиз. Круг, дуга или многоугольник сами по себе не определяют риски. Риски
определяет операция.

### Эскиз для вращения

Для вращения самый важный вопрос: есть ли один замкнутый профиль основного стиля
и ровно одна реальная ось вращения осевого стиля.

Вращение особенно чувствительно к helper-линиям. Человек в UI может выбрать
нужную область вручную, а automation часто передаёт весь sketch как profile.
Поэтому helper-линии должны быть вспомогательными или тонкими, а не осевыми.
Осевой стиль должен использоваться только для настоящей оси вращения, кроме
случаев, где ось нужна именно как графическая/симметрийная ось и не является
источником профиля.

Для вращения надо заранее решить, где находится ось относительно профиля, какие
радиусы измеряются до каких точек, и какие точки имеют смысл как inner/outer
границы. У `disc_spring` важным уроком было то, что простая деталь вращения
становится стабильной, когда есть один operation sketch, один замкнутый профиль
основного стиля и одна axis-line осевого стиля. У `diaphragm_spring` важным
уроком стало то, что похожий по виду контур может иметь значительно более
сложную смысловую базу: OD, base zero, body ID, ID, bend radius и full height не
должны выводиться из “примерно очевидных” точек.

Для вращения geometry-only gate обязателен: сначала чистый замкнутый профиль
основного стиля должен вращаться вокруг оси осевого стиля без параметрического
шума. Только потом можно добавлять размеры и переменные.

### Эскиз для выдавливания или выреза

Для выдавливания и выреза главный вопрос: какую область должна выбрать операция.
Обычно это должен быть один замкнутый профиль основного стиля. Если в sketch есть
несколько замкнутых областей, пересекающиеся helper-линии или несколько контуров,
automation может выбрать не то, что выбрал бы человек.

Простые hole/groove/flat-style эскизы полезны как пример: даже когда форма
несложная, размеры и constraints должны иметь смысловые имена. Но для сложных
эскизов этого недостаточно. Надо заранее определить, является ли это один
замкнутый профиль, несколько независимых профилей, или несколько операций,
которые лучше разделить.

Если деталь требует нескольких областей, лучше предпочесть несколько sketches и
несколько операций, чем один “умный” sketch, где KOMPAS должен угадать регион.

### Эскиз-профиль для sweep/evolution

Для sweep/evolution профиль должен быть локальным, замкнутым и простым. Его
задача — описать сечение, а не компенсировать путь. У пружин это проявилось в
правиле: wire profile лучше размещать на финальном конце `full_path_sequence`, с
локальным центром `[0, 0]`, а не таскать старые in-sketch offsets по радиусу
пружины.

Профиль sweep обычно должен быть отдельным от пути. Если профиль начинает знать
слишком много о глобальном радиусе, фазе, hook-side или старой точке привязки,
он становится хрупким. Для compression, conical, torsion и extension springs
стабильнее оказался подход, где финальный path sequence считается каноническим,
а профиль ставится на его реальный конец.

Для такого эскиза главный gate — не только “профиль замкнут”, но и “профиль
поставлен на правильный конец правильного пути”.

### Эскиз-путь для sweep/evolution

Путь — это незамкнутый контур, а не профиль. У него другие риски: порядок
сегментов, физическое начало и конец, направление обхода, фаза спирали,
локальная система координат, сопряжения между сегментами, trimming и fillet
result edges.

Опыт spring generators показывает, что для пути особенно опасны неявные
договорённости. Например, hook-specific anchor может работать для одного типа
крючка, но ломаться при независимой композиции left/right hooks. Поэтому path
sequence должен быть каноническим и явно описанным: откуда начинается, где
заканчивается, какие сегменты входят в финальный контур, какие являются
временными источниками, а какие результатами native операций.

Для path sketch или path operation надо отдельно фиксировать, является ли объект
логическим исходником или selectable result edge. Это особенно важно для native
fillet/trimming, где визуально правильный объект может быть неправильным
членом итогового контура.

### Auxiliary/reference sketch

Вспомогательный эскиз не должен случайно становиться операционным. Его задача —
дать опоры, точки, плоскости, направления или измерительные базы.

Если вспомогательная геометрия нужна только для размеров, её надо явно отделять
от operation sketch. Если она остаётся внутри operation sketch, она должна иметь
вспомогательный или тонкий стиль и должна пройти preflight как не мешающая
рабочему контуру.

### Эскиз с проекционным базированием

Проекционное базирование может использоваться как в operation sketch, так и во
вспомогательном эскизе. Его признак — геометрия текущего эскиза отсчитывается от
спроецированного внешнего объекта, а не от собственной локальной базы.

Для такого эскиза надо отдельно указать projected source и projected result.
Projected result не обязан быть рабочей геометрией. Если он нужен только как
anchor для построений, он должен быть вспомогательным/тонким. Если операция
должна использовать именно projected edge или projected contour, это надо
отдельно зафиксировать и выполнить его стилем, соответствующим потребителю.

Главный риск проекционного базирования — ложная уверенность. Координаты
спроецированного объекта могут совпадать с ожидаемыми, но связь может быть
потеряна, создана не к тому объекту или после rebuild уехать вместе с другой
геометрией. Поэтому для таких эскизов нужен readback не только координат, но и
самого факта projection/constraint, насколько это доступно.

## Локальные правила по типам геометрии

Примитивы геометрии не должны создавать отдельные большие ветки протокола, но
они включают дополнительные осторожности.

Дуги требуют явного описания start, end, center и direction. Нельзя полагаться
на интуицию “эта дуга очевидно идёт туда”. В KOMPAS направление дуги уже давало
ошибки: визуально близкая дуга может создать другой сегмент контура. Для
операционного профиля или траектории дуги надо проверять через live/readback, а
не только через формулу координат.

Сопряжения требуют понимания, являются ли они sketch-геометрией, native 3D
fillet, trimming result или selectable result edge. Для 3D-путей это особенно
важно: использовать контейнер операции как элемент контура и использовать его
результирующие рёбра — не одно и то же.

Окружности и профили сечения должны быть максимально локальными. Если окружность
wire profile находится на anchor plane, её центр в эскизе обычно должен быть
локальным нулём, а не глобальным смещением, принесённым из старой реализации.

Симметрия полезна только если ясно, относительно чего она задана. Ось симметрии,
ось вращения, строительная ось и измерительная база — разные вещи. Их нельзя
объединять только потому, что они выглядят как “линия посередине”.

## Переменные и формулы

Таблица переменных должна быть частью инженерного интерфейса, а не дампом всех
внутренних вычислений генератора.

Ведущие переменные — это параметры, которыми модель должна управляться извне:
диаметр, толщина, высота, радиус гиба, длина, число витков, pitch, wire diameter.

Производные переменные допустимы, когда они помогают читать модель или нужны для
формул размеров. Но производная переменная должна проходить простой тест: если
человек увидит её в KOMPAS, он поймёт, зачем она нужна? Если нет, лучше не
выносить её.

Отдельная опасность — информационные углы, длины и offsets, которые выглядят
полезно, но имеют сложную геометрическую зависимость. В `diaphragm_spring`
`DIA_CA1` и `DIA_TIP_A1` сначала казались полезными, но корректные формулы для
текущей схемы оказались завязаны на толщину и смещённую внешнюю точку. Такие
переменные лучше удалить, чем публиковать как сомнительную правду.

Если COM API не принимает формулу при создании объекта, это не повод отказываться
от параметризации. В проекте уже есть паттерн numeric fallback -> update ->
operation variable binding -> update. Но такой паттерн надо применять только к
осмысленным параметрам, а не ко всему подряд.

## Ограничения и размеры

Ограничения должны фиксировать смысловую геометрию, а не спасать неясную.

Если constraint нужен, надо понимать, какую инженерную правду он выражает:
горизонтальность базы, совпадение центра гиба, касательность дуги, равенство
радиусов, привязка к оси. Ограничение “чтобы solver успокоился” опасно, если за
ним нет физического смысла.

Размеры должны накладываться на именованные targets. Индекс линии или дуги может
поменяться, порядок создания может измениться, а смысловой target должен
остаться. Это особенно важно для long-running generators: через несколько дней
мы уже не помним, почему `line_7` была толщиной, а `line_8` — контрольной высотой.

Размер считается успешным только если он не просто применился, но и оставил
контур в корректном состоянии. Применённый dimension может разорвать профиль,
сломать траекторию, создать самопересечение или переместить точку в неправильную
сторону. Поэтому после размерного этапа нужен preflight, а не только счётчик
`applied_count`.

Для параметрического эскиза нормальная цель — полная определённость. Эскиз,
который остаётся недоопределённым, может выглядеть правильно в одном наборе
параметров и неожиданно уехать при другом. Поэтому после constraints и dimensions
надо проверять `ConstraintsState`/`sketch_state`, если такой readback доступен.
Если KOMPAS сообщает under-defined, это не обязательно мгновенная ошибка
геометрии, но это повод остановиться и понять, какая свобода осталась.

Исключение возможно только осознанно. Например, если `ConstraintsState` в сложном
эскизе ведёт себя нестабильно после update/reopen, это надо зафиксировать как
known risk и опираться на дополнительные факты: profile/path preflight,
operation success, applied dimensions, readback геометрии. Молчаливый пропуск
полной определённости недопустим.

## Проверки и gates

Для сложного эскиза нужны несколько gates. Они не должны быть тяжёлыми, но они
должны запрещать движение вперёд поверх грязной основы.

Первый gate — смысловой. Можно ли словами описать тип рабочего контура
(замкнутый профиль или незамкнутая траектория), его стиль линий, точки,
вспомогательные элементы и ведущие параметры? Если нельзя, кодить рано.

Второй gate — geometry-only. Операция должна работать на чистой геометрии без
полной параметризации и с правильными стилями линий. Если revolve/extrude/sweep
не работает на этом этапе, constraints не помогут.

Третий gate — после constraints. Эскиз должен сохранять тот же рабочий контур.
Если ограничения меняют топологию или заставляют operation видеть другой регион,
надо вернуться к схеме.

Четвёртый gate — после dimensions. Все размеры могут быть applied, но это не
достаточно. Для замкнутого профиля нужны closure/preflight checks: замкнутость,
отсутствие gaps, branches, лишних компонент и self-intersections. Для
незамкнутой траектории нужны свои проверки: одно начало, один конец, правильное
направление обхода, отсутствие лишних ответвлений и разрывов.

Пятый gate — определённость эскиза. Для параметрического эскиза ожидаемое
состояние — fully defined. Если full-defined недостижим или `ConstraintsState`
даёт нестабильные результаты, это должно быть записано как исключение с
альтернативными доказательствами устойчивости.

Шестой gate — после variables. Таблица переменных должна быть минимальной и
понятной. Удаление мусорных derived variables — это не косметика, а часть
качества модели.

Седьмой gate — live operation и readback. Модель должна не только построиться, но
и пережить сохранение/переоткрытие настолько, насколько это требуется для текущей
задачи.

## Когда надо остановиться

Есть несколько признаков, что работа пошла не туда.

Если приходится добавлять helper-линию, чтобы исправить проблему операции, надо
сначала спросить: какой у неё стиль и не загрязняет ли она operation sketch?

Если меняется смысл базовой точки, нельзя попутно чистить переменные или
добавлять constraints. Это отдельный refactor топологии.

Если переменная выглядит красиво, но её формула требует сложной обратной
геометрии, она подозрительна. Лучше оставить расчёт внутри генератора или убрать
переменную.

Если один sketch начинает обслуживать несколько разных операций или регионов,
надо рассмотреть разделение на несколько sketches.

Если эскиз базируется от проекции, но projected source или constraint нельзя
подтвердить, нельзя считать эскиз завершённым только по совпадению координат.

Если live CAD и readback расходятся с ожиданиями, приоритет у readback/live
фактов, а не у предположений по API.

Если `ConstraintsState` выглядит нестабильно, нельзя считать это единственным
источником истины. Нужно смотреть на operation success, profile preflight,
размеры, readback и геометрию вместе.

## Как этот документ связан с CAD_PATTERNS.md

`CAD_PATTERNS.md` хранит конкретные проверенные уроки: симптомы, причины,
правила, known examples. Например: один operation sketch с одним рабочим
контуром, вспомогательные линии не осевым стилем, direction semantics для дуг,
profile_preflight, operation-variable binding.

Этот документ должен быть уровнем выше. Он описывает порядок мышления и работы,
в который эти паттерны включаются. Если найден новый конкретный баг или правило
COM API, его место в `CAD_PATTERNS.md`. Если найден новый этап проектирования
сложного эскиза, его место здесь.

## Минимальный результат перед реализацией

Перед тем как сложный эскиз превращается в генератор, у нас должен быть хотя бы
такой текст:

```text
Operation consumer:
Contour class: closed profile / open path / auxiliary contour
Main contour order:
Line style map: main / axis / auxiliary
Base anchor: origin / coordinate axis / base plane / circle center / projection
Projection sources and constraints:
Axis/path/profile ownership:
Construction/helper geometry:
Named semantic points:
Driving variables:
Derived variables kept deliberately:
Variables deliberately not exposed:
Geometry-only gate:
Post-dimension/preflight gate:
Full-definition target or exception:
Live/readback gate:
Known risky assumptions:
```

Это не финальная агентская форма. Это человеческий контракт. Его задача — сделать
так, чтобы дальнейшая реализация была переводом уже понятной схемы в код, а не
одновременным изобретением схемы, API-вызовов и диагностики.

## Как развивать документ

Документ должен оставаться коротким по смыслу, даже если со временем станет
длиннее по примерам. В него не надо складывать все технические детали KOMPAS API.
Для этого есть `CAD_PATTERNS.md`, `sketch-diagnostics.md` и отчёты по отдельным
модулям.

Когда очередной сложный эскиз занимает слишком много времени, после завершения
надо спросить не только “какой паттерн добавить”, но и “на каком этапе протокола
мы должны были заметить проблему раньше”. Если ответ найден, этот документ надо
уточнить.
