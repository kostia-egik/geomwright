# Разработка и проверка изменений

[English](../en/development.md) · [Русский индекс](README.md) · [Правила вклада](../../CONTRIBUTING.md) (EN)

## Подготовка изменения

Прочитайте [архитектуру](architecture.md), нужные [CAD-паттерны](../../CAD_PATTERNS.md)
(EN) и контракт семейства. Определите слой L1–L4 и разделите владельцев геометрии,
workflow, bridge и presentation. Перед правкой проверьте `git status` и сохраните
сторонние изменения. Временные пробы храните в ignored-каталоге
`experiments/spikes/`; незавершённые модули не выводите в MCP.

Перед созданием или существенным расширением законченного CAD-модуля прочитайте
[регламент модулей](module-development.md). Он определяет общий контракт
Studio/генератор/MCP и критерии готовности, включая пользовательский ввод,
маркировку реконструкций, техническое превью и рациональную параметризацию.

В PowerShell из каталога клона:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[ui]" pytest
```

Для CAD-проверок также настройте интерпретатор и сессию по [инструкции установки](setup.md).

## Узкие проверки

Выберите тесты затронутого контракта; bridge-тест здесь приведён как пример:

```powershell
.\scripts\check_change.ps1 -TestPath tests/test_bridge_runner.py -TimeoutSeconds 60
```

Gate проверяет `git diff --check`, равенство bridge-копий, компиляцию выбранных
модулей, маркеры машинных путей/ключей и выбранные тесты. `-Keyword` сужает pytest;
`-Packaging` собирает wheel. `-Full` явно включает полный набор при обоснованной
необходимости и пишет сводки в `test-results/`. Deadline каждого subprocess по
умолчанию — 600 секунд, переопределение — `-TimeoutSeconds`; это не срок всего gate.

Для другой конечной команды:

```powershell
.\.venv\Scripts\python.exe scripts/run_bounded.py --timeout 60 -- .\.venv\Scripts\python.exe -m pytest tests/test_bridge_runner.py -q
```

Watchdog закрывает stdin, собирает вывод и останавливает принадлежащие ему дочерние
процессы; timeout возвращает 124. Постоянный фоновый сервер в него не оборачивайте.
Для Studio используйте `python -m geomwright.studio --background --no-browser`
по инструкции установки.

## Доказательства по типу изменения

Для детерминированной host-логики нужны узкие тесты значимых контрактов: формулы,
нормализация, топология, схемы и передача ошибок. Объединяйте существующее покрытие;
избегайте сгенерированных примеров и широких комбинаторных матриц.

Host pytest не должен обращаться к живому CAD. Защита в `tests/conftest.py`
блокирует реальные bridge-вызовы, включая фоновые задания. Для Studio routes
передавайте fake adapters и дожидайтесь окончания их jobs. COM-поведение требует
отдельных живых проверок: compile/import, явный target и подтверждение записи,
snapshot/readback, save/reopen и визуальная проверка, когда её требует контракт.
Различайте подтверждение исходником, host-тестами и live CAD; pytest не доказывает
успешное построение в КОМПАС.

## Документация и упаковка

Обновляйте подробный контракт-владелец и обе страницы EN/RU одним изменением.
Следуйте [правилам локалей](../README.md#languages-and-ownership); синхронизируйте
имена API, defaults, ограничения и уровень доказательств. На длинные источники
ссылайтесь, не переводя всю историю реализации.

Сохраняйте byte-identical `bridge/kompas_bridge.py` и packaged-копию. При изменении
упаковки проверяйте assets. Сгенерированный CAD, readback dumps, credentials,
машинный `opencode.json` и временные скрипты не включайте в commits. Проверьте
финальный diff и явно сообщите о пробелах в проверке.
